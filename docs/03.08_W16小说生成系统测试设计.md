## 核心洞察

### 为什么不直接做 Web 应用？

1. **验证优先于界面** — 先确认 4-agent 逻辑能跑通，再加 UI
2. **快速迭代** — CLI 改一行代码立即测试，Web 需要前后端联调
3. **参考项目学习** — 参考项目的核心逻辑都是 Python，直接对标
4. **自媒体准备** — 自媒体内容生产可以用 CLI 脚本批量生成

### 为什么是"混合方案"？

- **快速验证路径**：Python 脚本 + JSON 文件存储，验证 4-agent 流程
- **同步搭框架**：建立 monorepo 结构、定义 Schema、写测试框架
- 两条线并行，周末前有可运行的闭环 + 有架构基础

## 前提假设

1. **Story State Core 是唯一真相源** — 所有状态变更都通过它
2. **Truth Files 只是投影** — 不是主存储，只用于展示和上下文
3. **4-Agent 契约已锁定** — Planner/Writer/Reviewer/Committer 的 I/O Schema 明确
4. **Claude API 可用** — 用 Claude 作为 Agent 实现的基础

## 推荐方案

### 方案 A：快速验证路径（主线）

**目标**：周三前有一个完整的多章节生成闭环

**技术栈**：
- Python 3.11
- SQLite（存储 Story State Core）
- Claude API（4 个 Agent 实现）
- JSON（Truth Files 投影）
- pytest（测试框架）

## 成功标准

### 必须达成

1. ✅ 能创建一个小说项目并初始化 Story State Core
2. ✅ 能生成第 1 章的规划（Planner 输出）
3. ✅ 能基于规划生成第 1 章的草稿（Writer 输出）
4. ✅ 能对草稿进行审查（Reviewer 输出）
5. ✅ 能将审查后的章节回写到 Story State Core（Committer 输出）
6. ✅ 能连续生成 3-5 个章节，每章都走完整闭环
7. ✅ 所有状态变更都有事件日志记录
8. ✅ 能导出 Truth Files（Markdown 格式）

### 加分项

- 能检测并警告 unresolved DSL 引用
- ✅ **能做局部改写（不重新生成整章）** — `packages/agents/src/local_rewrite.py`，2026-04-15
- ✅ 能计算基础的追读力评分（Reviewer 集成）
- ✅ 有最小回归测试集（10 个测试，2026-04-15）

## 开放问题

1. **Claude API 的 Token 预算** — 连续生成 5 章需要多少 Token？是否需要降级策略？
2. **上下文长度** — 随着章节增加，Story State Core 会变多大？检索规则如何避免超长？
3. **局部改写的边界** — 如何定义"局部"？改写时如何保证不污染上下文？
4. **Reviewer 的评分标准** — 追读力、一致性、AI 风格等如何量化？

## 风险与缓解

| 风险 | 影响 | 缓解方案 |
|------|------|--------|
| Claude API 调用失败 | 闭环中断 | 本地 fallback、重试机制、错误恢复 |
| 上下文污染 | 后续章节质量下降 | 严格的检索规则、定期清理、版本化 |
| Schema 不匹配 | 集成失败 | 提前定义、单元测试、契约测试 |
| 状态回写冲突 | 数据不一致 | 乐观锁、事件日志、可审计 |
