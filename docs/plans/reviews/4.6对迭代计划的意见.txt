# AI网文创作平台迭代实施规划 · 综合审查报告

这份规划在整体方向上是清醒且克制的，"先闭环→再韧性→后写作智能→再平台化→最终整合"的路线与两份调研报告的核心结论高度一致。但在**优点整合的完整性**和**若干工程细节的覆盖深度**上，仍有值得补强的空间。以下是逐层审查结论。

---

## 🔍 一、整合优点的覆盖度审查

### 各阶段吸收来源对照表

| 项目 | 核心优点 | 规划中的吸收状态 | 评估 |
|------|---------|----------------|------|
| **InkOS** | Truth Files + Hook治理 + 去AI腔 + 多模型路由 | Phase A/B/C 均有明确吸收 | ✅ 覆盖较完整 |
| **webnovel-writer** | 追读力系统 + RAG双路召回 + 中文网文约束 | Phase A/C 有吸收，但 RAG 评估体系较薄 | ⚠️ 部分覆盖 |
| **NovelForge** | Schema驱动 + @DSL注入 + 卡片式工作台 | Phase A 有 @DSL，但 Schema 驱动生成未单独强调 | ⚠️ 部分覆盖 |
| **AI_NovelGenerator** | GUI分步可控 + 向量检索 + 模型兼容广 | 几乎未明确吸收 | ❌ 基本缺失 |

---

### 1.1 InkOS — 吸收较好，但有两处遗漏

规划对 InkOS 的吸收是四个项目中最完整的，但以下两点**未被显式纳入**：

**① 多模型路由（Multi-model Routing）**

InkOS 的核心工程亮点之一是"Writer 用 Claude，Auditor 用 GPT-4o"，即按 Agent 职责做模型分级路由，兼顾质量与成本。

规划全程未提及模型路由策略，这在 Phase D 扩展到多 Agent 后会成为**成本失控的隐患**。

**② 风格指纹克隆（Style Fingerprint）**

InkOS 的 `inkos style analyze` 可提取作者风格统计指纹。规划在 Phase C 提到"写作风格与卡片策略库"，但未明确是否包含**从参考文本提取风格特征**的能力，这是中文网文连载中"保持作者语感一致"的关键工具。

---

### 1.2 webnovel-writer — RAG 评估体系覆盖不足

规划在 Phase B 提到"检索质量基线（Recall@K / DSL命中率 / 关键信息保留率）"，这是好的开始。但对照调研报告中 webnovel-writer 的 RAG 双路召回（Embedding + Rerank + BM25 fallback）体系，规划**缺少以下内容**：

- 离线 RAG 评估管线（召回质量退化如何被自动发现）
- Rerank 服务的集成时机（Phase A 还是 Phase B？）
- 检索对象的语义定义：不是任意 chunk，而是"可引用事实"（人物关系、伏笔、资源账本、章节摘要）

这一缺失在 Phase A 就会产生影响，因为 `retrieval rules` 和 `prompt assembler` 的质量直接决定第一个闭环的可用性。

---

### 1.3 NovelForge — Schema 驱动生成未被充分吸收

规划提到 `@DSL resolver` 和 `versioned schema`，但 NovelForge 最核心的优点是**字段级流式生成 + JSON Schema 校验 AI 输出**，即：

> 每个 Agent 的输出都被 Schema 约束，生成失败可以字段级重试，而不是整章重来。

规划中的 Reviewer → `patch_plan` 结构（Phase C）是类似思路，但没有把"Schema 驱动的结构化输出校验"作为**贯穿全链路的工程原则**显式声明。这会导致在 Phase A 实现时，各 Agent 的输出格式可能是松散的，后期再收紧成本很高。

---

### 1.4 AI_NovelGenerator — 几乎未被吸收

调研报告明确指出 AI_NovelGenerator 的核心价值是**交互门槛**（GUI 分步可控）和**模型兼容广**（OpenAI 兼容接口）。规划的整合表中 Phase E 写了"四者整合"，但在具体阶段中，AI_NovelGenerator 的优点几乎没有对应的落地动作。

这里需要区分两种情况：

- 如果规划定位是"技术平台优先，GUI 是后期交互层"，那么 AI_NovelGenerator 的 GUI 思路可以延后到 Phase D/E，**但需要显式说明**
- 如果 Phase A 就需要有用户可操作的界面，那么"分步可控"的交互设计应该更早引入

---

## 🔍 二、规划内部的结构性问题

### 2.1 Phase A 的"最小闭环"定义偏重工程，轻写作质量

Phase A 的验收标准是：

> 能生成整章草稿 / 能做局部改写 / 能对 unresolved DSL 做警告 / 能回写到 State Core

这些都是**工程可交付物**，但缺少一条**写作质量的最低验收线**，例如：

- 生成的章节是否满足基本的中文网文语感要求？
- Reviewer 的输出是否有最低的有效建议率？
- 是否有哪怕一个"黄金章节快照"作为质量基线？

调研报告（小说架构调研与对比）明确建议：

> 短期就要建立 prompt 版本化与最小评估集（10–20 个固定题材/固定设定/固定章节目标的用例）

规划在 Phase B 才提到 `regression harness`，但**写作质量的回归基线应该在 Phase A 就埋下**，否则 Phase B 的"质量基线"没有对比起点。

---

### 2.2 Phase B 的"事件语义标准化"与 Phase A 的 event log 存在重叠风险

Phase A 要求实现 `event log 基础版`，Phase B 要求做 `事件语义标准化`（event_type / actor_type / correlation_id / causation_id）。

这两步的边界不够清晰，容易导致：

- Phase A 实现了一套"够用但不规范"的 event log
- Phase B 要对其做破坏性重构，而不是增量升级

**建议**：在 Phase A 就按 Phase B 的语义字段定义 event log schema（哪怕只记录少数事件类型），避免后期迁移成本。这是"一次设计，分步填充"的原则。

---

### 2.3 Phase C 的"追读力深入接入"缺少量化验收标准

Phase C 的追读力验收标准是：

> "用户能明显感觉到'更懂网文，而不只是更会写句子'"

这是**主观感受**，不是可验证的验收标准。对照 webnovel-writer 的追读力系统（Hook密度 / Cool-point分布 / 微兑现率 / 债务追踪），这些指标是可以被量化计算的。

建议补充：
- Hook 密度基线（每 N 字至少 1 个 Hook）
- 债务回收率目标（已埋伏笔的回收比例）
- anti-AI-tone 误判率阈值（按题材设定容忍上限）

---

### 2.4 Phase D 的扩展顺序合理，但缺少"不扩展的条件"

规划列出了 Phase D 的扩展前提（5 个条件），这很好。但没有说明：

> 如果某个前提条件在预期时间内未能满足，Phase D 应该如何处理？是继续等待，还是有降级路径？

这在项目管理上是一个风险敞口，建议补充"Phase D 的触发条件与延迟策略"。

---

## 💡 三、改进建议汇总

以下是按优先级排列的改进建议：

### 高优先级（影响 Phase A/B 落地质量）

**① 在 Phase A 就定义结构化输出契约**

所有 Agent 的输入/输出格式在 Phase A 就应该用 JSON Schema 约束，哪怕初期 Schema 很简单。这是从 NovelForge 应该吸收的最核心工程原则，也是防止 Phase D 多 Agent 扩展时 I/O 契约混乱的根本保障。

**② 在 Phase A 建立最小写作质量基线**

建立 5–10 个"黄金章节测试用例"（固定题材 + 固定设定 + 固定章节目标），作为后续所有 prompt 迭代的回归起点。这与 `minimum regression harness` 并列，而不是延后到 Phase B。

**③ Phase A 的 event log 直接按 Phase B 语义字段设计**

避免两阶段之间的破坏性重构。字段可以先空着，但 schema 要对齐。

---

### 中优先级（影响 Phase C/D 的质量上限）

**④ 补充多模型路由策略**

在 Phase B 或 Phase C 中明确：哪些 Agent 用什么级别的模型，如何根据任务重要性和成本做路由决策。这直接影响系统的可持续运营成本。

**⑤ 追读力指标量化**

Phase C 的追读力验收标准需要从"用户感受"升级为可计算的指标阈值。

**⑥ 明确 AI_NovelGenerator 的"分步可控"思路的吸收时机**

在规划中显式说明：GUI 分步交互的设计思路在哪个 Phase 引入，或者为什么不引入。

---

### 低优先级（影响 Phase E 的完整性）

**⑦ 补充 Phase D 的延迟触发策略**

明确"如果前提条件未满足，Phase D 如何处理"。

**⑧ 风格指纹能力的归属**

明确"从参考文本提取风格特征"这个能力在哪个 Phase 实现，对应 InkOS 的 `style analyze` 功能。

---

## 📊 四、总体评估

```
整合完整性：  ████████░░  78%   — AI_NovelGenerator 和 Schema 驱动覆盖不足
工程韧性设计：████████░░  80%   — Phase B 设计扎实，但 event log 边界需厘清  
写作质量保障：██████░░░░  60%   — 质量基线和追读力量化是最大短板
实施节奏合理性：█████████░ 88%  — "先闭环再韧性"的顺序与调研结论高度一致
风险管理：    ███████░░░  70%   — Phase D 触发条件和模型成本风险未充分覆盖
```

**核心结论**：这份规划的**路线方向是正确的**，"先闭环→再韧性"的顺序判断与两份调研报告的独立结论完全吻合，说明规划者对系统复杂度有清醒认识。主要改进空间集中在三点：**Phase A 就要埋下质量基线的种子**、**结构化输出契约要贯穿全链路**、**追读力验收标准要从主观感受升级为可量化指标**。这三点不需要改变路线，只需要在现有框架内做局部补强。
