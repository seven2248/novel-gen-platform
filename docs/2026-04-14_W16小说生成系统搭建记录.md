### 核心模块说明

**JSON Schema（6个）**
- `story_state.schema.json` — Story State Core 完整结构
- `chapter_state.schema.json` — 章节状态机枚举
- 4 个 Agent I/O Schema — Planner/Writer/Reviewer/Committer 的输入输出契约

**Story State Core**
- `StoryState` — 项目级状态（角色、关系、钩子、资源、章节摘要）
- `ChapterState` — 章节级状态（状态机：not_started → planning → drafting → reviewing → pending_confirmation → committed → published）
- `EventLog` — 语义事件日志（correlation_id、causation_id）

**4-Agent**
- `Planner` — 根据章节目标和当前状态生成结构化规划（beats、tone_hint）
- `Writer` — 根据规划生成完整章节草稿
- `Reviewer` — 审查一致性、风格、追读力，输出可执行建议
- `Committer` — 生成状态 diff 预览（不直接写入，到用户确认才执行）

**CLI 入口**
```bash
python -m packages.agents.src.cli "生成第1章：主角进入宗门"
```

## 遇到的问题与解决

### 问题 1：测试文件语法错误

**现象**：`test_main_chapter_flow.py` 第 19 行出现 `SyntaxError: invalid syntax`，pytest 无法收集测试。

**原因**：中文字符串中包含了 ASCII 双引号包裹的中文（如 `"青云宗"`），Python 将其解析为不完整的字符串字面量。

**解决**：将所有中文内容中的双引号改为括号拼接（`"..." "..."` 形式），避免在同一字符串内出现未转义的中文引号。

---

### 问题 2：测试 mock 策略多次失败

**现象**：单元测试中 mock 没有生效，真实 API 被调用，导致测试耗时 140 秒且失败。

**尝试方案**：

1. **patch `anthropic.Anthropic`** — 失败，因为 `ClaudeClient.__init__` 在 patch 之前就已经创建了 `Anthropic` 实例

2. **patch `packages.agents.src.base.ClaudeClient`** — 失败，patch 路径在测试收集阶段不可达

3. **patch `anthropic.Anthropic.messages.create`** — 失败，`messages` 是 `functools.cached_property`，无法在类层面 patch

4. **最终解决**：在 `base.py` 中内置 mock 机制
   ```python
   _mock_state = {"enabled": False, "responses": {}}

   def set_mock_responses(responses: dict):
       _mock_state["enabled"] = True
       _mock_state["responses"] = responses

   def reset_mock():
       _mock_state["enabled"] = False
   ```
   `conftest.py` 的 `autouse=True` fixture 在测试前调用 `set_mock_responses()`，各 Agent 模块通过 `_mock_state` 判断是否使用 mock 数据。

**核心教训**：当被测代码在模块加载时创建资源（网络连接等），patch 必须发生在导入之前，或采用依赖注入/全局注册表模式。内置 mock 开关是最稳妥的方案。

---

### 问题 3：schema_validator.py 路径解析错误

**现象**：`load_schema()` 无法找到 schema 文件，报 `FileNotFoundError`。

**原因**：Windows 路径中的中文字符在 `Path.__init__` 中被错误处理，导致父目录路径解析出错的错误。虽然最终验证通过，但路径构造逻辑脆弱。

**解决**：明确注释了每一级 `parent` 的含义（`parent.parent.parent / "contracts"`），确保路径从正确的基准点出发。

### Prompt Markdown 污染问题修复

**问题**：gemma4:26b 在 JSON 输出外包裹 ` ```json ... ``` ` markdown，破坏解析。

**根因**：prompt 里只说"输出 JSON"，模型默认加 code block 包装。

**修复**：在 `planner.py`、`writer.py`、`reviewer.py` 的 system prompt 里加了一条硬规则：
```
- **只输出纯 JSON**，不要使用 markdown 代码块包裹，不要有 ``` 符号
```
修复后 4 个阶段输出全部干净，无 markdown 污染。

### 关键设计决策讨论

**生成方式**：当前是有约束的提示词生成，非纯自由生成。

- Planner 根据章节目标 + story_state 生成结构化规划（硬约束 beats 顺序）
- Writer 系统 prompt 里写了：角色一致、避免 AI 腔、结尾要有钩子
- Reviewer 给出评分和可执行建议
- Committer 生成 diff 预览，不自动写回

**限制**：风格约束是软性的，无硬性评分卡点；长篇上下文靠 story_state dict 注入，信息量有限。

**Prompt 外置化**：
- `base.py` 里有 `load_prompt(name)` 接口，设计意图是从文件加载 prompt
- 但目前没用上，system prompt 硬编码在 `.py` 文件里
- templates 目录不存在

**决策：跑通测试轮次后再重构 prompt 外置化**。理由：
1. gemma4:26b 对齐风格未摸透，会大量改 prompt，现在重构等于对空气设计
2. 只需搬字符串 + 改加载逻辑，工作量小（2 小时），收益在验证后才明确
3. 当前主线是"跑通第一轮可复用测试"

时序建议：先跑完 W16 小说主线（多章节、局部改写各一圈）→ 记录期间改过的 prompt → 回头做 prompt 外置化 + 菜单测试界面。
