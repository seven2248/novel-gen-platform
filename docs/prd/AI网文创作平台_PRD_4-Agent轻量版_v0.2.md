# AI网文创作平台 PRD · 4-Agent 轻量版 v0.2

## 1. 产品定位

这是一个面向中文网文创作的 AI 写作工作台。

它的核心不是“全自动写一本书”，而是帮助作者在长篇创作中稳定完成以下闭环：

- 查清当前状态
- 写出当前章节
- 对局部进行精修
- 检查一致性与追读力
- 将确认后的结果回写到统一状态核心

一句话定位：

> 一个强 Manual、轻 Auto、面向长篇连载的中文网文创作台。

---

## 2. 版本升级目标

v0.1 已经完成了范围收敛，但仍偏概念级。

v0.2 的目标不是增加更多模块，而是把以下三类工程缺口补齐：

1. 定义 4 个 Agent 的输入输出契约
2. 把“局部改写”从模糊功能改成独立快车道
3. 为检索、评审、回写和提示词迭代补齐最小可实施规则

本版仍坚持：

- `Story State Core` 是唯一真相源
- `Truth Files` 只是投影视图
- `4-agent` 仍是推荐主架构
- 不引入完整 10-agent 流水线
- 不把完整 Event Sourcing 拉进 v1 核心

---

## 3. 目标用户

### 3.1 核心用户

1. 中文网文作者
2. 有设定、有大纲，但容易写崩的长篇创作者
3. 不懂技术，但愿意依赖 AI 辅助创作的内容生产者

### 3.2 用户特征

- 想让 AI 帮忙，但不想被 AI 接管
- 更看重“可控性”和“稳定性”
- 经常遇到角色漂移、伏笔遗忘、节奏失衡
- 高度依赖“局部精修”而不是整章重写

---

## 4. 核心问题

### 4.1 当前痛点

1. 写到中后期，角色、设定、资源容易自相矛盾
2. 常见 AI 工具只能整段重写，局部修订不稳定
3. 追读力反馈不结构化，无法转化为明确动作
4. 长篇上下文越来越长，模型容易遗忘
5. Prompt 一改就可能质量漂移，缺少回归机制

### 4.2 产品要解决的事

1. 建立统一状态核心，作为唯一真相源
2. 提供章节工作台，支持“查、写、改、审、回写”闭环
3. 用 4-agent 轻量闭环提供规划、写作、审查和回写
4. 用局部改写快车道支持高频精修
5. 用最小评估集和 Prompt 版本化避免质量退化

---

## 5. 产品原则

1. `统一状态核心优先`
2. `Manual-first，Auto-light`
3. `卡片是策略层，不是状态层`
4. `追读力要参与决策，不只是展示分数`
5. `局部改写优先保证速度和稳定性`
6. `所有状态回写都必须可解释、可预览、可拒绝`

---

## 6. 核心架构

### 6.1 Story State Core

系统维护一套统一状态核心，包括：

- 角色状态
- 关系状态
- 主线/支线进度
- 伏笔债务
- 资源账本
- 章节摘要
- 风格约束
- 卡片使用记录

这套状态是唯一真相源。

### 6.2 Truth Files

Markdown 版 Truth Files 只作为：

- 用户可读界面
- 模型上下文投影
- 导出材料

不作为主存储，不承担写入权威。

### 6.3 最小事件日志

第一版不引入完整 Event Sourcing，但必须保留最小事件日志：

- 章节规划生成
- 草稿生成
- 局部改写
- Reviewer 结果
- Committer 回写预览
- 用户确认结果

作用：

- 支持回看
- 支持问题定位
- 为未来升级到完整事件化提供基础

---

## 7. 4-Agent 轻量闭环

系统只保留四个主 Agent：

1. `Planner`
2. `Writer`
3. `Reviewer`
4. `Committer`

主流程：

```text
章节目标 -> Planner -> Writer -> Reviewer -> 用户确认 -> Committer
```

---

## 8. Agent I/O 契约

本节为开发前必须锁定的最小协议。

### 8.1 Planner

**输入**

- 用户章节目标
- 当前章节位置
- 相关状态摘要
- 已挂载卡片
- 追读力提醒

**输出 Schema**

```json
{
  "chapter_goal": "string",
  "beats": ["string"],
  "cards_attached": ["card_id"],
  "context_hints": ["string"],
  "required_hooks": ["hook_id"],
  "tone_hint": "string"
}
```

### 8.2 Writer

**输入**

- Planner 输出
- Prompt Assembler 组装的上下文块
- 当前写作模式（整章 / 局部）

**输出 Schema**

```json
{
  "draft_text": "string",
  "used_hooks": ["hook_id"],
  "used_cards": ["card_id"],
  "open_questions": ["string"]
}
```

### 8.3 Reviewer

**输入**

- 草稿文本
- 状态核心摘要
- 中文写作约束
- 追读力规则

**输出 Schema**

```json
{
  "consistency_issues": [],
  "style_issues": [],
  "readability_score": 0,
  "hook_strength_score": 0,
  "actionable_suggestions": [],
  "risk_level": "low|medium|high"
}
```

### 8.4 Committer

**输入**

- 用户确认后的终稿
- Reviewer 输出
- 当前状态快照

**输出 Schema**

```json
{
  "state_diff": {
    "add": [],
    "update": [],
    "remove": []
  },
  "projection_refresh_targets": [],
  "warnings": []
}
```

## 9. 章节工作台

工作台包含四个核心区域：

1. `章节编辑区`
2. `状态侧栏`
3. `桥段卡片面板`
4. `审核与建议面板`

### 9.1 状态侧栏必须展示

- 当前章节目标
- 当前涉及角色状态
- 当前伏笔债务
- 最近章节摘要
- 风格约束提醒
- 当前章节状态

### 9.2 章节状态机

每章必须处于明确状态：

```text
未开始 -> 规划中 -> 草稿中 -> 审核中 -> 待确认 -> 已提交 -> 已发布
```

价值：

- 用户知道当前卡在哪一步
- 局部改写等子流程有落点
- 后续多人协作更容易扩展

---

## 10. 局部改写快车道

局部改写不走完整 4-agent 主链路，而走独立轻量链路。

### 10.1 适用场景

- 自由改写
- 应用桥段卡片改写
- 风格修正
- 节奏补强
- 钩子补强

### 10.2 流程

```text
选中文本 + 改写意图
  -> Context Assembler
  -> Writer（局部模式）
  -> Diff Validator
  -> 用户确认
  -> Committer（字段级 diff 回写）
```

### 10.3 设计原则

- 响应速度优先于整章生成
- 只校验改动影响区域
- 回写必须是字段级 diff，而不是全章覆盖

---

## 11. 检索与上下文装配

### 11.1 检索来源

- Timeline Recall
- Vector Recall
- BM25 Recall
- @DSL 显式引用

### 11.2 @DSL 支持范围

- `@[角色:xxx]`
- `@[地点:xxx]`
- `@[伏笔:xxx]`
- `@[卡片:xxx]`

### 11.3 检索规则

开发前必须明确以下策略：

1. `Top-K`
   - 默认整章生成与局部改写使用不同的 Top-K

2. `优先级`
   - 显式 @DSL 引用高于普通语义召回
   - 章节最近摘要高于远距离历史片段

3. `截断规则`
   - 优先保留显式引用与章节相关状态
   - 其次保留近期章节摘要
   - 最后才保留远距片段

### 11.4 Prompt Assembler 责任

Prompt Assembler 必须负责：

- 去重
- 排序
- 截断
- 拼装上下文块

不能把这些逻辑分散到各个 Agent 内部。

---

## 12. 追读力决策机制

追读力不能只作为展示分数，必须参与 Reviewer 决策。

### 12.1 最小指标

- `hook_strength`
- `payoff_balance`
- `pace_tension`
- `novelty_density`

### 12.2 Reviewer 行为阈值

| 分数区间 | Reviewer 行为 |
|---|---|
| `>= 80` | 正常通过，记录分数 |
| `60-79` | 标记弱项，并给出可执行建议 |
| `< 60` | 强提示用户，建议应用节奏类或钩子类卡片 |

### 12.3 输出要求

所有追读力建议必须是可执行建议，而不是空泛评价。

示例：

- “中段节奏偏松” 不够
- “建议在第 3 节后插入一次角色关系反转或章节末钩子” 才算有效

---

## 13. 状态回写规则

### 13.1 基本原则

- 未确认前不得污染全局状态
- Committer 只回写有证据支持的状态变化
- 回写必须可预览

### 13.2 回写粒度

- 整章流程：章节级 + 字段级 diff
- 局部改写流程：字段级 diff

### 13.3 幂等性规则

同一份确认稿重复提交，不得造成重复写入：

- 不重复新增伏笔
- 不重复追加章节摘要
- 不重复覆盖相同状态

### 13.4 防呆要求

当用户手动大改文本时，Committer 不能直接盲写：

- 必须生成回写预览
- 必须标记低置信度状态变化
- 必须允许用户拒绝回写某些 diff

## 14. 功能范围

### 14.1 必做功能

1. 项目创建与题材预设
2. Story State Core
3. 章节工作台
4. 局部改写快车道
5. 桥段卡片挂载
6. 双路召回 + @DSL 四类引用
7. 追读力决策
8. 一致性检查
9. 轻量 Auto 流程
10. Markdown Truth Files 导出
11. 最小事件日志
12. Prompt 版本化与最小评估集

### 14.2 不在首版范围

1. 全自动写完整本书
2. 10-agent 高度分工流水线
3. 全量知识图谱
4. 桌面端打包
5. VS Code / Claude Code 插件
6. 团队协作和多角色权限体系
7. 完整 Event Sourcing

## 15. 评估与回归机制

### 15.1 最小评估集

Phase 1 就要建立 10 到 20 个固定用例。

固定输入包括：

- 世界观设定
- 角色档案
- 章节目标
- 风格约束

固定验证包括：

- 结构化输出是否符合 Schema
- 是否出现设定冲突
- 是否出现禁用词
- 章末是否存在钩子

### 15.2 Prompt 版本化

每次改动以下内容都必须记录版本：

- Planner Prompt
- Writer Prompt
- Reviewer Prompt
- Prompt Assembler 规则

### 15.3 回归目标

每次 prompt 或流程改动后，都要能快速回答：

- 写作质量变好了还是变差了
- 一致性冲突有没有增加
- 去 AI 腔有没有退化

---

## 16. 非功能要求

### 16.1 性能

- 单次章节上下文组装应在可接受范围内完成
- 局部改写响应必须优于整章生成

### 16.2 稳定性

- 状态回写必须幂等
- 检索结果需可解释
- Prompt Assembler 必须可测

### 16.3 可理解性

- 用户能看懂 Reviewer 为什么判定有问题
- 用户能看懂 Committer 为什么建议回写某个状态 diff

---

## 17. 风险

1. 如果 Agent 契约不清，4-agent 会退化成黑盒串联
2. 如果局部改写没有快车道，最高频功能会最慢
3. 如果检索规则太松，噪音会快速污染写作质量
4. 如果没有回归机制，Prompt 迭代会越来越玄学
5. 如果状态回写没有防呆，用户会失去对系统的信任

---

## 20. 总结

4-Agent 轻量版依然是推荐路线。

这次 v0.2 升级的重点，不是把系统变大，而是把它补成一份真的可以开工的工程级 PRD。

它的本质依然是：

> 先把“稳定状态 -> 精准检索 -> 可控生成 -> 局部修订 -> 状态回写”这条闭环跑顺，再考虑扩张自动化深度。
