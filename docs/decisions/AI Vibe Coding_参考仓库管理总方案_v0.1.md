# AI Vibe Coding 参考仓库管理总方案

## 1. 目标

这份方案解决的不是“怎么让 AI 多看几个 GitHub 仓库”，而是：

- 怎么让 AI 在一个受控边界内使用参考项目
- 怎么避免 AI 被参考仓库带偏
- 怎么让参考代码服务于你的 PRD 和实施计划，而不是反过来决定你的产品

一句话原则：

> 先以我方文档定方向，再用本地参考仓库学结构，最后让 AI 在约束下实施。

---

## 2. 总体原则

### 2.1 文档优先，代码参考次之

你的项目里优先级最高的是：

1. `PRD`
2. `实施计划`
3. `决策记录`
4. `我方代码`
5. `参考仓库`

也就是说，参考仓库只能回答：

- 别人是怎么解决类似问题的
- 哪种结构更成熟
- 哪种职责拆分更清晰

它不能直接决定：

- 你的产品边界
- 你的命名
- 你的状态模型
- 你的技术选型

### 2.2 本地参考仓库优先

调研阶段可以让 AI 在线看 GitHub。  
正式实施阶段，参考项目应该下载到本地。

原因：

- 本地目录结构更完整
- 可以稳定搜索和对比
- 可以沉淀自己的笔记
- 可以避免 AI 每次联网查询时上下文飘移

### 2.3 参考仓库只能“学模式”，不能“搬实现”

正确的参考方式是：

- 学状态分层
- 学 Agent 职责划分
- 学工作流顺序
- 学交互组织方式

不正确的参考方式是：

- 直接复制实现代码
- 沿用别人项目的命名污染你自己的系统
- 不顾许可证和技术栈差异直接复用

---

## 3. 推荐目录结构

建议你把参考仓库独立放一层，不要混进主代码目录：

```text
your-project/
├─ docs/
│  ├─ prd/
│  ├─ plans/
│  └─ decisions/
├─ src/
├─ tests/
├─ references/
│  ├─ repos/
│  │  ├─ inkos/
│  │  ├─ webnovel-writer/
│  │  ├─ novelforge/
│  │  └─ ai_novel_generator/
│  ├─ notes/
│  │  ├─ repo-summary.md
│  │  ├─ capability-map.md
│  │  ├─ data-structures.md
│  │  └─ do-not-copy.md
│  └─ snapshots/
│     └─ repo-versions.md
└─ prompts/
   ├─ implement-with-references.md
   └─ compare-reference-patterns.md
```

---

## 4. 每层目录的作用

### 4.1 `docs/`

这里是你自己的真相源。

要放：

- PRD
- 实施计划
- 决策记录
- 版本差异说明

AI 每次开工前，必须先看这里。

### 4.2 `references/repos/`

这里放原始参考仓库。

要求：

- 保持原始目录结构
- 不在里面直接改业务逻辑
- 不把其中代码混入 `src/`

### 4.3 `references/notes/`

这里是“你学到了什么”的沉淀层。

推荐至少有这四份文件：

- `repo-summary.md`
- `capability-map.md`
- `data-structures.md`
- `do-not-copy.md`

### 4.4 `prompts/`

这里存你给 IDE 里 AI 用的固定提示词。

作用：

- 减少每次重复沟通
- 固定 AI 的阅读顺序
- 强制 AI 先出对照表再写代码

---

## 5. 参考仓库接入流程

每个新参考仓库接入时，按这个顺序走：

1. 记录仓库名、地址、许可证、最后同步时间
2. 写一句话总结：它最值得借鉴什么
3. 记录不适合借鉴什么
4. 记录和你当前产品最相关的模块
5. 把这些内容沉淀到 `references/notes/`

推荐模板：

```md
## inkos

- 仓库地址：
- 许可证：
- 最后同步时间：
- 核心价值：
- 最值得借鉴的模块：
- 不建议直接借鉴的部分：
- 与我方系统的映射关系：
```

---

## 6. AI 实施前的标准顺序

每次要做一个功能时，都要求 AI 遵守固定顺序：

1. 先读 `docs/` 里的相关 PRD 和实施计划
2. 再读 `references/notes/` 的总结文件
3. 再读 `references/repos/` 中真正相关的模块
4. 先输出“参考对照表”
5. 经过确认后再写代码

不要让 AI 一上来直接扫参考仓库并开始实现。

---

## 7. 参考对照表标准格式

每次实施前，让 AI 先输出这个：

```md
# 参考对照表

## 本次目标
- [本次功能]

## 参考仓库
- [仓库 A]
- [仓库 B]

## 借鉴点
- [点 1]
- [点 2]

## 不借鉴点
- [点 1]
- [点 2]

## 我方映射
- 参考点 -> 我方哪个模块

## 风险
- [风险 1]
- [风险 2]
```

这个动作的意义很大，因为它会强迫 AI 从“抄代码”切换到“解释设计”。

---

## 8. 你在 IDE 中给 AI 的总提示词

建议固定为一份模板，放到 `prompts/implement-with-references.md`：

```md
本次任务目标：
[写本次要实现的功能]

执行规则：
1. 先阅读 docs 中与本任务相关的 PRD、实施计划、决策文档。
2. 再阅读 references/notes 中的仓库总结和能力映射。
3. 再阅读 references/repos 中最相关的参考模块。
4. 先输出“参考对照表”，不要直接写代码。
5. 在我确认后再开始实施。

实施时必须遵守：
- docs 是我方唯一产品真相源
- references 只用于借鉴思路，不直接复制实现
- 优先保持我方命名、数据结构和模块边界一致
- 每次说明本次实现参考了哪个仓库的什么模式
```

---

## 9. 仓库维护规则

### 9.1 定期同步

建议按周或按里程碑同步参考仓库，而不是每次临时联网查。

### 9.2 建立版本快照

在 `references/snapshots/repo-versions.md` 里记录：

- 仓库名
- 同步日期
- commit hash 或 tag
- 本次同步原因

### 9.3 区分“长期参考”和“临时调研”

- 长期参考：放进 `references/repos/`
- 临时调研：只记到 `notes/`，不一定 clone

### 9.4 单次任务不要同时重度使用太多参考仓库

建议每次实现只重度参考 1 到 2 个仓库。  
超过 2 个，AI 很容易把风格和结构混杂。

---

## 10. 风险与禁区

### 10.1 常见风险

1. AI 用参考仓库覆盖了你的产品边界
2. AI 只学到代码表面，没学到系统结构
3. 不同参考仓库的风格被混成一锅
4. 许可证风险被忽略

### 10.2 明确禁区

不要这样要求 AI：

- “参考这几个项目，直接帮我实现一版”
- “照着这个仓库改成我的版本”
- “尽量复用别人的代码”

要这样要求：

- “先总结这几个项目各自解决的问题”
- “先说明我们借鉴什么，不借鉴什么”
- “先把设计映射到我方架构，再开始写代码”

---

## 11. 推荐执行口诀

你可以直接记住这一句：

> 我方文档定方向，本地参考学结构，AI 先做对照表，再进入实施。

这套流程的目的不是变慢，而是防止 AI 在看起来很快的情况下，把项目越写越偏。
